## Lessons from the actual 2026-05-25 execution

Read this BEFORE re-using as a v0.1.15 template:

1. **Path B is the primary path on this prod, not the fallback.**
   §3.2 stops the orchestrator, which makes Path A's
   `vectis update plan/apply` return "orchestrator unreachable". Path
   A would only work if we *first* booted the new orchestrator
   container (with v0.1.14 image) so it can self-orchestrate the rest.
   Re-using this runbook: either skip §3.2 entirely and go Path A
   against the running v0.1.12 orchestrator (risk: it self-applies
   mid-prep), or accept that §3.2 commits us to Path B.

2. **The "uncomment customer_one_key Step 0" only works AFTER §3.4.**
   v0.1.12 strict-YAML-rejects the key (the incident pattern). Order
   that works: pull images → install v0.1.14 binary → THEN uncomment
   the key → THEN compose down + up (which boots v0.1.14 reading the
   uncommented secret cleanly). v0.1.14's binary has the inline
   forward-compat catch-all so any future field is tolerated, but the
   2026-05-25 cutover hit this with the existing field.

3. **The host is 5.8 GiB, not 8 GB.** BL silently overprovisions the
   legacy `a-3020` slug (~50% bonus RAM). Pick `resources.profile:
   small` not `production`. See [[reference_binarylane_vps_specs]] for
   the full sizing analysis and upgrade-ladder cost.

4. **`vectis config diff` doesn't accept `--db-host`** — only
   `config generate` does. To preview a Path-B update before the live
   overwrite, use the scratch-dir dance:
   ```bash
   sudo /usr/local/bin/vectis config generate \
     --db-host $(docker inspect vectis-postgres \
       --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}') \
     -o /tmp/vX.Y.Z-gen
   sudo diff /etc/vectis/docker-compose.yml /tmp/vX.Y.Z-gen/docker-compose.yml
   ```
   then `cp` from `/tmp/vX.Y.Z-gen/` into `/etc/vectis/` and
   `/var/vectis/generated/` once happy. CLI alignment is on the
   v0.1.15 backlog.

5. **§5.4 Real Buy-Pro click test isn't applicable on a PRO install.**
   The Free-tier CTA only renders when the install is on Free. This
   prod install is on PRO (Customer #1) so the CTA never shows.
   Verified by-proxy via `POST /api/v1/account/upgrade-checkout-session`
   authenticated as super_admin. For a future fresh-Free-install
   cutover (Customer #2 or test installs), the §5.4 click-through
   would render normally.

6. **Mail-flow downtime was ~60 seconds** during compose down → up,
   matching the runbook estimate. Real timing of the full cutover
   was ~45 min including all pre-flight + memory updates, ~10 min
   for the actual §4 window.

7. **Prune old images BEFORE pulling new ones — the host fills up.**
   (Lesson from the v0.1.17 cutover, 2026-05-29.) Every past release
   leaves its 8 images on the host; after ~16 releases the 60 GB root
   fs hit **0 MB free** the moment §3.3 pulled the new tags. A full root
   fs is a live-prod risk (Postgres WAL/logs) and also breaks tooling.
   §1.4 now includes a `df -h /` headroom check and §3.3 now prunes all
   but current/target/`latest` before pulling. Bulk `docker rmi` on prod
   needs explicit operator authorization. See
   [[feedback_prod_disk_image_accumulation]].

## 3. Pre-cutover steps (T+4, after §2 green)

### 3.1 Apply the config edit

```bash
sudo -e /etc/vectis/config.yaml
# Add the resources.profile block from §1.6
sudo diff /etc/vectis/config.yaml.pre-v0.1.14 /etc/vectis/config.yaml
# expect: only the resources.profile addition
```

### 3.2 Confirm self-heal is currently disabled, then disable watchdog

The orchestrator's network-drift watchdog (rc60+) fires every 60s.
During the cutover the compose layout will change (mem_limit additions)
and we don't want the watchdog to take corrective action mid-flight.

**Decision point:** Stopping the orchestrator commits us to Path B in
§4.1 (Path A's `vectis update plan/apply` needs the orchestrator
running). Path B is fine — that's what 2026-05-25 used — but if you
specifically want Path A, SKIP this step.

```bash
# Check current state
docker exec vectis-orchestrator pgrep -af watchdog || true

# Stop the orchestrator's reconcile loop ahead of the bump.
# Self-heal will resume once the new orchestrator boots in §4.
# Note: in-process watchdog (no separate procs visible via pgrep).
docker stop vectis-orchestrator
```

### 3.3 Prune old images, then pull all 8 ahead of time

**Prune first.** Old release images accumulate and will fill the root fs
on the pull (this bit the v0.1.17 cutover — see Lesson #7). Use the GC
routine, which also clears the exited `vectis-apply-helper-*` containers
that pin old orchestrator images (the deeper root cause a plain `rmi`
can't touch). It keeps the running version, the previous stable, and
`latest`. Bulk removal on prod is a deliberate, operator-authorized action.

```bash
./scripts/prune-images.sh            # dry-run: review what it will remove
./scripts/prune-images.sh --apply    # then execute
df -h /                              # confirm comfortable headroom before pulling
```

No `rmi -f` is used, so Docker refuses to remove an image a running
container uses — the live stack is safe. The script keeps the newest 2
stable tags per repo; pass `--keep 3` to retain an extra rollback target.

**Then pull.**

```bash
for svc in api orchestrator postfix dovecot rspamd clamav cert-extractor webmail; do
  docker pull "ghcr.io/veltara-works/vectis-$svc:v0.1.14"
done
docker images --format 'table {{.Repository}}\t{{.Tag}}\t{{.Size}}' \
  | grep ':v0.1.14'
# expect all 8 cached locally
```

Pulling now (before the actual cutover) gets the network transfer out
of the way and dramatically shortens the downtime window.

If a forward-staged secret was commented out for v0.1.12-strict-YAML
safety (e.g. `customer_one_key` before the 2026-05-25 incident fix),
uncomment it NOW — after §3.4 installed the new binary but before §4.
The new binary's `KnownFields(true)` decoder tolerates the field;

## 4. Cutover (T+4, the actual window)

Estimated window: **5-10 minutes** of restart churn, ~60 seconds of
mail-stack downtime once compose down/up is issued.

### 4.1 Run the orchestrator upgrade

Two paths exist. **Path B is the primary path when §3.2 has stopped
the orchestrator** (which is the runbook's default flow). Path A only
works if the v0.1.12 orchestrator is still running — see the Lessons
section above.

**Path B — manual compose down/up (primary path on this prod):**

The actual subcommand is `config generate` (not `--plan`/`--apply` —
those are the orchestrator-driven flags). The `--db-host` flag is
required when running from the host because secrets.yaml has
`host: postgres` (the docker DNS name, unreachable from the host).

```bash
# Preview first — render into scratch dir, diff against live
DB_IP=$(docker inspect vectis-postgres \
  --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}')
sudo /usr/local/bin/vectis config generate \
  --db-host "$DB_IP" -o /tmp/v0.1.14-gen
sudo diff /etc/vectis/docker-compose.yml /tmp/v0.1.14-gen/docker-compose.yml | head -200
# Expect:
#   - 8 image tag bumps v0.1.12 → v0.1.14
#   - mem_limit additions per service (v0.1.13 capacity bundle)
#   - valkey: --maxmemory + allkeys-lru (P7-H2)
#   - new rspamd/milter_headers.conf file
#   - NO mount-stripping
#   - NO unexpected per-service config diffs

# Commit the preview to live
sudo cp -av /tmp/v0.1.14-gen/docker-compose.yml /var/vectis/generated/docker-compose.yml
sudo cp -av /tmp/v0.1.14-gen/docker-compose.yml /etc/vectis/docker-compose.yml
sudo cp -av /tmp/v0.1.14-gen/promtail/promtail.yml /var/vectis/generated/promtail/promtail.yml
sudo cp -av /tmp/v0.1.14-gen/webmail/roundcube.config.php /var/vectis/generated/webmail/roundcube.config.php
sudo cp -av /tmp/v0.1.14-gen/rspamd/milter_headers.conf /var/vectis/generated/rspamd/milter_headers.conf

# Live cutover
sudo docker compose -f /etc/vectis/docker-compose.yml down --timeout 30
sudo docker compose -f /etc/vectis/docker-compose.yml up -d
```

**Path A — `vectis update plan/apply` (only if §3.2 was SKIPPED):**

```bash
sudo vectis update plan
# Review the plan. Expected diffs as in Path B's diff above.
```

## 6. Rollback (only if §5 fails irrecoverably)

```bash
# 1. Stop the broken stack
sudo docker compose -f /etc/vectis/docker-compose.yml down --timeout 30

# 2. Restore config + secrets + compose
sudo cp -a /etc/vectis/secrets.yaml.pre-v0.1.14 /etc/vectis/secrets.yaml
sudo cp -a /etc/vectis/config.yaml.pre-v0.1.14 /etc/vectis/config.yaml
sudo cp -a /etc/vectis/docker-compose.yml.pre-v0.1.14 /etc/vectis/docker-compose.yml

# 3. Roll the binary back
# (keep a copy of the v0.1.12 binary somewhere — pull from R2 if needed)
curl -fsSL -o /tmp/v0.1.12.bin https://dl.vectismail.com/v0.1.12/vectis-linux-amd64
sudo install -m 0755 /tmp/v0.1.12.bin /usr/local/bin/vectis
vectis version    # expect v0.1.12

# 4. Restart on the old compose
sudo docker compose -f /etc/vectis/docker-compose.yml up -d

# 5. Restore postgres ONLY if there is data corruption — most cutover
#    failures don't touch the DB. Don't restore unless you have evidence
#    the failure mode involved DB writes.
gunzip < /var/vectis/backups/pre-v0.1.14-*.sql.gz \
  | docker exec -i vectis-postgres psql -U vectis_api -d vectis
```

## 8. Cutover-only contraindications (when to abort, even mid-window)

- Postgres `pg_dump` snapshot file is < 100K or unreadable — abort §1.3,
  no cutover until DB is in a known-good snapshot state.
- `df -h /` shows insufficient headroom and the §3.3 prune doesn't recover
  enough for the image pull — abort and resolve disk first (a full root fs
  risks Postgres writes; don't push through it).
- §1.2 smoke harness fails — abort, re-verify build.
- §2.3 R2 binary sha mismatch — abort, re-run release workflow.
- §4.2 any container stuck `starting` > 5 min — abort and §6 rollback.
- §5.1 `Memory: 0` reported for any service — cgroup ceilings didn't
  apply, fall back to `resources.profile: small` and re-Apply, or §6
  rollback if it persists.
- §5.3 smoke harness fails post-deploy — the in-product upgrade endpoint
  isn't live; abort and §6 rollback.
