**Type:** Backup restore test (isolated) — first execution of the
[disaster-recovery-runbook](disaster-recovery-runbook.md) drill (audit item P8-H1).
**Operator:** Veltara Works (agent-assisted)
**Result:** ✅ PASS — a real production backup restored to a working system in an

## Method

In-place restore on live prod is destructive (drops/recreates the DB) and was
**deliberately not** performed — we are days from the HN launch. Instead, the
drill restored a **real prod backup** into a throwaway sandbox, which proves the
archive is restorable without risking production:

1. **Backup (non-destructive).** Created a real vectis-format backup via the
   running api container — `docker exec vectis-api vectis backup create` —
   exercising the production backup path (pg_dump + tar + AES-256-GCM). Output:
   `vectis-20260530-015015.tar.gz.enc`, 941.8 KB (DB dump 5.28 MB pre-archive).
2. **Isolated restore.** Spun up a throwaway `postgres:17-alpine` + temp dirs,
   seeded the app roles (as `vectis install` would), and ran the production
   restore code against the real archive via the gated harness
   `TestDRDrillRealArchive` (`internal/backup/restore_integration_test.go`).
   Service control (docker compose stop/start) was stubbed — there is no stack
   to control in the sandbox; that step is orchestration, not data integrity.
   Encryption key = `secrets.api.secret` (no dedicated `backup_encryption_key`
   is configured, so the code falls back to the API secret).
3. **Verify.** Asserted core tables restored + populated, mail/DKIM/config files
   restored, and `secrets.yaml` absent (it must never be in a backup).
4. **Teardown.** Destroyed the sandbox; `shred`-removed the decrypted-capable
   archive copy. No production data left the host.

## Findings

### F1 — Backups are written to the api container's ephemeral layer (HIGH)

`/var/vectis/backups` is **not** a mount on the `vectis-api` container, so
backups land on the container's writable layer. Every cutover does
`compose down/up`, which **destroys the container and any backups in it.**
The runbook (§8) lists `/var/vectis/backups` as the backup location, implying
host/volume persistence — it is not wired that way.

**Remediation:** add a persistent mount (named volume or host bind) for
`/var/vectis/backups` to the api service in the orchestrator's compose template,
regenerate compose, and recreate the api container. Until then, any backup must
be `docker cp`-ed out immediately to survive a recreate.

### F2 — Scheduled backups are disabled (HIGH)

`config.yaml` has `backup.enabled: false`, so the daily `0 2 * * *` job never
runs — there were zero vectis-format archives on the host before this drill.
The RPO of 24h in the runbook is currently not being met.

**Remediation:** set `backup.enabled: true` — but only **after F1**, otherwise
scheduled backups accumulate on ephemeral storage and vanish on the next
cutover. Consider also off-host copies (runbook §5).

### F3 — No dedicated backup encryption key (LOW)

`secrets.backup_encryption_key` is unset, so encryption falls back to
`api.secret`. This works, but couples backup confidentiality to the API secret —
rotating the API secret would orphan older backups. Consider setting a dedicated
`backup_encryption_key`.

## Remediation (2026-05-30, same day)

**F1 — FIXED.**
- Compose template now bind-mounts `/var/vectis/backups` on the api service
  (`internal/engine/templates/docker-compose.yml.tmpl`), asserted by
  `TestBackupsCompose_APIBindMount`. Permanent from v0.1.18.
- Applied to prod immediately: added the mount to the live compose
  (`/etc/vectis/docker-compose.yml` + the generated copy; backups saved with
  `.pre-backups-mount.*` suffix) and recreated the api container
  (`up -d --no-deps api`). **Proven durable** — created a backup, force-recreated
  the api container, the backup survived. Stack healthy after (11/11, webmail 200).
- ⚠️ The manual compose edit could be stripped if a `vectis config apply` runs on
  the **v0.1.17** binary before v0.1.18 (its template lacks the mount). The next
  cutover is v0.1.18, which carries the mount in-template, making it permanent.

**F2 — FIXED (two-part).**
- In-app scheduler implemented (`internal/backup/scheduler.go`, robfig/cron/v3),
  wired into the api lifecycle, honours `backup.{enabled,schedule,retain_days}`,
  prunes old archives (keeps newest). Ships in v0.1.18.
- Immediate prod coverage via a **host-cron stopgap** (`deploy/stopgap/vectis-backup-cron.sh`
  → `/usr/local/bin/` + `/etc/cron.d/vectis-backup`, daily 02:00, 30-day
  retention). Tested: creates a durable backup on the host, logs to
  `/var/log/vectis-backup-cron.log`.

**At the v0.1.18 cutover (do both, atomically, to avoid double backups):**
1. Set `config.yaml` `backup.enabled: true` (schedule `0 2 * * *`, retain 30).
2. Remove the stopgap: `sudo rm -f /etc/cron.d/vectis-backup /usr/local/bin/vectis-backup-cron.sh`.

**F3 (dedicated backup encryption key)** — still open, LOW.

## Repeatable harness

The drill is reproducible via the gated test (skipped by default):

```bash

VECTIS_DRILL_ARCHIVE=/path/to/archive.tar.gz.enc \
VECTIS_DRILL_KEY=<api.secret> \
VECTIS_TEST_PG_HOST=... VECTIS_TEST_PG_PORT=... \
  go test -tags integration ./internal/backup/ -run TestDRDrillRealArchive -v
```
