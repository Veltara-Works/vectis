## 0. The headline you MUST remember — this is NOT a pure image-bump

v0.1.16 and v0.1.17 were mechanical "8 image-tag bumps, no structural
change" cutovers. **v0.1.18 is different in two ways that need operator
action in the window:**

1. **Activate the in-app backup scheduler.** The api binary now ships a
   cron scheduler (`internal/backup/scheduler.go`), but it only runs if
   `backup.enabled: true`. Prod's config still has `enabled: false`.
   **Flip it to `true` at cutover** (schedule `0 2 * * *`, retain 30 —
   already present in the config).
2. **Remove the host-cron stopgap in the same window.** A daily host
   cron (`/etc/cron.d/vectis-backup` → `/usr/local/bin/vectis-backup-cron.sh`)
   has been doing backups since 2026-05-30. The moment the in-app
   scheduler goes live, leaving the stopgap in place means **DOUBLE
   backups**. Remove the stopgap *together with* flipping `enabled: true`.

Plus one structural-but-already-staged change:

3. **The `api` service gains a `/var/vectis/backups` bind mount** (F1).
   v0.1.18's compose template carries it; prod's live compose already
   has it hand-added (commit `9dfa126`). So the diff gate should be
   clean. The order in §3 (install v0.1.18 binary *before* generating
   compose) is what guarantees the mount is NOT stripped — see
   [[feedback_cross_version_apply_strips_mounts]].

Everything else in v0.1.18 is binary/image content (no further config
or schema change). **No new secrets to stage** (unlike v0.1.14's
`customer_one_key`), and **no Buy-Pro click test** — prod is on PRO and
v0.1.18 changes nothing on the billing path.

## E. Execution notes (2026-06-02) — what actually happened

The cutover went clean (6/6 pre-flight green, textbook diff, ~55 s downtime,
all healthy in ~25 s, smoke 3/3, no drift). Five things worth keeping:

1. **cosign wasn't installed on prod** — fetched it to `/tmp` and ran from
   there (no system install). `verify-blob` + image `verify` both OK.
2. **Scheduler dump path ≠ on-demand CLI path.** The api server builds the
   backup Manager with a real DB pool → `dumpDBFn = dumpDatabase` (TCP
   `pg_dump --host postgres`, backup.go:161); the api image ships `pg_dump`
   17.10. The standalone CLI (`vectis backup create`) defaults to the
   docker-exec path. So: `docker exec vectis-api vectis backup create`
   **fails** (no docker in-container); host CLI as johnsmith **fails** on
   root-owned DKIM keys. On-demand = `sudo vectis backup create` or
